01 / NETWORK TROUBLESHOOTING

IP가 남아 있는데도 Pod를 만들 수 없었던 이유

남은 IP의 개수와 할당 가능한 주소 블록은 달랐습니다. IPAMD 로그로 Prefix 할당 실패를 확인하고, Node와 Pod의 주소 영역을 분리했습니다.

문제와 원인

CPU Worker가 ContainerCreating 상태에 머무르며 Pod IP 할당에 실패했습니다. 서브넷에는 가용 IP가 112개 남아 있어 단순한 IP 소진만으로 설명하기 어려웠습니다.

Pod 이벤트와 Node ENI 상태를 확인한 뒤 VPC CNI·IPAMD 로그를 추적해 InsufficientCidr 오류를 확인했습니다. Prefix Delegation은 정렬된 /28 블록 단위로 주소를 할당하는데, VPC Endpoint ENI와 Node별 예비 Prefix로 인해 서브넷이 단편화되어 할당 가능한 /28 블록이 남지 않았습니다.

해결 과정

  • Secondary CIDR 100.64.0.0/16에 AZ별 Pod 전용 서브넷을 만들고 Custom Networking으로 Node·Pod 주소 영역을 분리했습니다.
  • AZ별 ENIConfig를 연결하고, Karpenter의 Node 서브넷 탐색 대상에서 Pod 서브넷을 제외했습니다.
  • 이후 DNS 조회 실패를 양쪽 Node의 tcpdump로 추적해 보안 그룹 단계의 차단으로 좁혔습니다. Pod용 ENI와 CoreDNS Node 간 상호 허용 규칙을 추가했습니다.
  • 기존 VPC 대역만 허용하던 VPC Endpoint 보안 그룹에 Pod 대역을 추가해 SQS 연결 실패를 해결했습니다.

결과와 확인

새 Pod가 100.64.x.x 대역의 IP를 받아 ContainerCreating 상태를 벗어났습니다. Pod 할당 가능 주소를 AZ당 약 250개에서 약 3.2만 개로 확장하고, Node 서브넷은 Node당 IP 1개만 사용하는 구조로 바꿨습니다.

02 / WORKLOAD-DRIVEN AUTOSCALING

작업량에 맞춰 확장하고, 기본 용량은 보호하기

KEDA는 “얼마나 늘릴지”, 배치 정책은 “어디에 둘지”, Karpenter는 “어떤 Node를 공급할지”를 담당하도록 역할을 나눴습니다.

기존 구조의 한계

  • CPU 사용률 70% 기준 HPA가 GPU 연산 부하와 SQS 대기량 증가를 감지하지 못해 Scale-out이 되지 않았습니다.
  • 최소 replica가 1이어서 요청이 없어도 GPU·Batch가 상시 실행되었습니다.
  • Spot 도입 시 기본 처리 용량까지 회수될 위험이 있었고, GPU를 0개로 축소하면 첫 요청이 Node 공급과 모델 기동을 약 5분 기다렸습니다.

1. SQS 작업량을 기준으로 확장

KEDA로 확장 기준을 CPU에서 SQS로 바꾸고 visible·in-flight 메시지를 합산해 처리 중인 작업이 지표에서 누락되지 않도록 했습니다. 워크로드별 목표 큐 길이와 min/max replica를 설정하고, Pod가 Pending 상태가 되면 Karpenter가 CPU·GPU 요구사항에 맞는 Node를 공급하도록 구성했습니다.

2. 기본 용량과 추가 용량의 배치 분리

Base는 On-Demand 전용 NodePool에, Burst는 Spot을 선호하되 공급이 부족하면 On-Demand도 허용하는 NodePool에 배치했습니다. 단일 Deployment에 Mutating Webhook을 적용해 KEDA가 정한 Pod 수를 유지하면서 각 Pod의 배치 조건을 구분했습니다.

  • ConfigMap 예약과 resourceVersion 기반 충돌 재시도로 여러 웹훅 복제본이 Base를 중복 배정하지 않도록 했습니다.
  • 원본 Pod 템플릿을 On-Demand로 두고 failurePolicy: Ignore를 적용해 웹훅 장애 중에도 Pod 생성이 가능하도록 구성했습니다.
  • pod-deletion-cost로 같은 ReplicaSet에서 Burst가 먼저 삭제되도록 유도했습니다.

3. 유휴 비용과 첫 요청 대기시간의 균형

Batch·GPU는 기본적으로 min replica를 0으로 설정했습니다. GPU는 평일 08:30–20:00에 KEDA Cron으로 1개를 미리 띄우고, 업무 외 시간에는 0개로 축소해 첫 요청 대기와 유휴 비용을 함께 고려했습니다.

4. 축소와 Spot 중단에 대응

EventBridge와 중단 이벤트 전용 SQS로 Karpenter가 Spot 중단 경고를 받도록 구성했습니다. Worker 종료 시 새 작업 수신을 중단하고 진행 중인 작업을 마무리하며, 강제 종료된 작업은 SQS visibility가 만료되면 다시 수신하도록 했습니다. CPU·GPU Worker의 빈 Node만 정리해 실행 중인 작업을 보호했습니다.

03 / INCIDENT RESPONSE & CHATOPS

장애 조사부터 승인형 복구 검증까지

장애 근거를 모아 롤백 PR을 제안하고, 운영자가 승인·merge한 뒤 새 이미지의 Pod 상태까지 확인해 같은 Slack 스레드에 결과를 남겼습니다.

문제

단계별 큐와 Worker로 나뉜 파이프라인에서 장애를 조사하려면 큐 상태, Pod 이벤트, 최근 배포 이력을 따로 확인해야 했습니다. 롤백 이후에도 새 버전 반영과 Pod 정상 동작을 수동으로 확인하고 팀에 다시 알려야 했습니다.

Slack의 3초 응답 제한보다 LLM 응답이 오래 걸리면 요청이 재전달되어 모델 호출과 답글이 중복될 수 있었습니다. 질의응답과 장애 분석은 응답 속도·입력량·허용 비용도 달랐습니다.

1. 알림에 원인 배포 정보 연결

알림·배포 이벤트·운영자 명령을 하나의 큐로 받아 처리하고, 실제 Pod의 이미지 태그를 배포 저장소 커밋과 연결했습니다. 배포가 원인인 경우 규칙에 따라 롤백 PR 생성 버튼을 제공했습니다.

2. Merge 이벤트로 복구 확인 시작

롤백 PR의 merge 이벤트를 받아 Argo CD 동기화, 새 이미지 Pod의 Ready 상태와 재시작 횟수를 차례로 확인했습니다. Rolling update 중 기존 Pod 때문에 Ready 수가 정상으로 보일 수 있어 새 이미지의 Pod를 기준으로 판정했습니다.

3. 요청 접수와 비동기 처리 분리

Lambda는 요청 서명을 검증하고 SQS에 넣은 뒤 즉시 응답합니다. Worker는 요청별 처리 상태와 생성 결과를 DynamoDB에 저장해 재전달 시 재사용하고, 전송 결과가 불확실한 답글은 중복 전송하지 않도록 처리했습니다.

4. LiteLLM으로 모델·호출·비용 정책 분리

서비스별 키에 허용 모델, 분당 호출 수와 예산을 지정하고 질의응답은 빠른 모델, 장애 요약은 큰 모델로 고정했습니다. Redis로 프록시 간 호출 한도를 공유하고 모델에 도달하지 않은 실패는 재시도 횟수에서 제외했습니다.
